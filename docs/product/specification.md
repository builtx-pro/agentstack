# AgentStack: техническое задание

## 1. Задача
Разработчик получает от ИИ много экранов и изменений, но тратит время на поиск нужного состояния, передачу контекста и проверку результата. Заказчик и дизайнер обсуждают те же изменения в разных чатах. AgentStack объединяет просмотр, замечания, документацию и план в одном рабочем месте. Агент получает точную цель и текущую версию через API/MCP, человек проверяет результат рядом с исходным замечанием.

Это новый самостоятельный публичный движок. Клиентские проекты импортируются как приватные данные инсталляции. Исходный закрытый репозиторий и его история не публикуются.

## 2. Основной сценарий
1. Владелец запускает Docker Compose и создаёт администратора без общедоступного пароля по умолчанию.
2. Создаёт проект, назначает разработчика и заказчика, импортирует каталог экранов и ассетов.
3. Разработчик отсматривает сценарий, открывает экран: слева изображение/безопасное превью, справа обсуждение.
4. Оставляет замечание к конкретной версии. Заказчик может сделать то же самое или предложить фичу.
5. Агент по поручению человека получает контекст, правила и открытые задачи, берёт задачу во временную работу.
6. Агент исправляет исходный проект, проверяет изменение и отправляет результат с доказательствами и ссылкой на версию.
7. Человек принимает результат или возвращает замечание с пояснением. Все переходы сохраняются.

## 3. Проекты и доступ
- Администратор инсталляции видит все проекты, пользователей и настройки.
- Разработчик видит только проекты, в которые назначен; может менять каталог, документы и план, создавать агентские токены в пределах своих прав.
- Заказчик видит только назначенные проекты и явно доступные ему материалы; комментирует, предлагает и принимает изменения. Внутренние правила/документы ему недоступны.
- Доступ проверяется сервером к каждому объекту, файлу, счётчику, поиску, экспорту, истории и MCP-ответу. Недоступные объекты не раскрываются.
- По умолчанию проекты приватны. Основной вход по логину/паролю с cookie-сессией; приглашение содержит одноразовый токен, имеет срок и может быть отозвано.
- Красивый адрес проекта/поддомен может служить входной страницей, но не заменяет членство. Не нужны wildcard DNS и отдельный сервер для каждого заказчика.
- Сервисные токены ограничены проектом, операциями и сроком. Их отзыв действует немедленно. Секрет хранится хешем, показывается при создании один раз.

## 4. Каталог экранов
Стабильный ID, заголовок, описание, теги, вариант, палитра/тема, размер кадра, исходный путь, версия, скриншот, ссылка превью. Сценарий содержит упорядоченные шаги и альтернативные состояния. Один экран может встречаться в нескольких сценариях, но поиск не дублирует его.

Поиск по словам/ID/тегам, фильтры по сценарию, варианту, состоянию замечаний и архиву. Фильтры и выбранный объект сохраняются в URL. Равная высота карточек, компактные теги, счётчики обсуждений в единой нижней строке. Модалка не двигает сетку; закрытие справа, клавиатурная навигация, фокус остаётся внутри. На телефоне обсуждение под изображением внутри модалки.

Сравнение версий рядом; смена версии не переносит старое замечание на новую без явного контекста. Связь «изменено после замечания» помогает повторному ревью.

## 5. Библиотека ассетов
Иллюстрации, фотографии, иконки и другие визуальные материалы. Идентификатор, название, тип, теги, описание, варианты, версии файлов, размеры/тип, источник и лицензия при наличии. Поиск, фильтры, карточки, просмотр, скачивание по правам, комментарии и история. Экран может ссылаться на несколько ассетов; ассет показывает места использования. Замена файла создаёт новую версию, старые комментарии и файлы остаются доступны.

Иллюстрации и их обсуждения из текущего проекта обязательны к миграции. Не публиковать их в OSS-репозитории.

## 6. Общие обсуждения и задачи для агента
Цель: screen, asset, document, rule, wave, epic, story, sprint, feature, proposal. Замечание сохраняет целевой revision, текст, проверенного автора, дату, видимость, состояние и историю. Внутреннее обсуждение не показывается заказчику.

Состояния: open → in_progress → ready_for_review → resolved; blocked как отдельный флаг; возврат в open с причиной. Назначение агенту имеет срок и не является вечной блокировкой. Создание идемпотентно; обновление с expectedVersion. Обычное сохранение комментария не запускает ИИ и не расходует платные API.

Для ready_for_review требуются описание результата и evidence. UI явно различает «сообщил агент», «проверил CI» и «принял человек». Агент не принимает собственную работу. Человек может вернуть задачу в работу. Реплики, изменения текста и статусы версионируются; скрытие/архив не уничтожает историю.

## 7. Документы и правила
Дерево документов: README, продукт, архитектура, API, эксплуатация, правила, инструкции и навыки агентов. Markdown-редактор с просмотром, сохранение по версии, diff, история и восстановление. Raw HTML/скрипты не исполняются. Чекбоксы в документах сохраняются как версия документа.

Разработчик редактирует, заказчик оставляет комментарий/предложение. Изменение правил, влияющих на агента, требует явного принятия человеком; агент может предложить diff. Каждый запуск задачи фиксирует версию правил. Копирование context bundle и экспорт Markdown/JSON позволяют работать с любой LLM даже без MCP.

## 8. Планирование
Wave объединяет epics; epic содержит stories. Sprint собирает stories для выполнения; feature связывает несколько stories. Предложения фич/исправлений имеют обсуждение, решение и связь с принятым work item. Одно предложение можно конвертировать один раз без дублирования.

Редактирование в вебе, статусы backlog/ready/in_progress/review/done, отдельный blocked, приоритеты, исполнитель, acceptance checklist, связи и комментарии. Иерархия не допускает циклов и чужих проектов. Архивирование не удаляет данные.

История — единица проектного прогресса. Общий процент = число уникальных завершённых активных stories / все активные stories. Фичи и спринты не создают повторный вклад. Чекбоксы показывают локальную готовность, но не закрывают story автоматически. Пустой scope показывает «нет задач», а не 100%. Заказчик видит только разрешённый ему scope.

## 9. Дашборды
Обзор всех разрешённых проектов и обзор проекта: прогресс, статусная раскладка, активный спринт, волны/эпики, открытые замечания, ожидает приёмки, блокеры, последние изменения. График накопленного выполнения и изменений scope строится из настоящей истории. Без истории показывать пустое состояние, не вымышленные данные. Графикам соответствуют доступные текстовые значения/таблицы.

## 10. Сквозное версионирование и архив
Все редактируемые бизнес-объекты, включая проекты, членство, сценарии, экраны, ассеты, документы, правила, work items и комментарии, получают версии и audit events. Одно изменение объекта и его запись истории атомарны. Событие хранит actor, source (web/CLI/MCP/import), timestamp, request ID, before/after либо безопасный diff, связь с задачей и commit/release при наличии.

Секреты, хеши паролей/токенов и приватные инфраструктурные значения в diff не попадают. История соблюдает текущие права объекта; старое публичное состояние не раскрывает сейчас закрытый объект. Историю нельзя редактировать через обычные CRUD-ручки.

Restore создаёт новую версию на основании выбранной старой. Восстановление доступа/прав не выполняется общим restore контента. Архив/разархивирование сохраняет ссылки и обсуждения; удалённый из импорта объект становится архивным, а не исчезает. Для каждой сущности видны «кто/когда/что изменил», diff и существующие версии. Файлы ассетов неизменяемые, заменяются новой ссылкой/версией.

## 11. Агентская интеграция
MCP stdio, REST API, CLI и переносимый context bundle используют один контракт и права. Tools: capabilities, projects, context, search/read targets, open notes, claim, submit result, documents/propose edits, planning/progress, history. Настройка через переменные окружения, без токенов в репозитории.

AGENTS.md — основной источник инструкций; Claude, Cursor, Copilot, Gemini и другие поддерживающие текстовые правила инструменты получают короткие адаптеры. Skills/recipes: review feedback, review assets, plan sprint, update docs, verify change, release review. Машинные capabilities и схема импорта описывают поддерживаемые операции. Нет обещания универсальной автоматической настройки каждого клиента.

Git-интеграция: локальный CLI импортирует/экспортирует manifest и Markdown, фиксирует branch/commit/worktree как контекст. Синхронизация явная, с baseVersion/baseSha и конфликтами. Сервер не запускает произвольные shell-команды и не получает SSH-ключи разработчика. Изменение правил через импорт тоже проходит human approval.

## 12. Установка и эксплуатация
Один монорепозиторий, Docker Compose: приложение + PostgreSQL + опциональный TLS proxy. CLI bootstrap, миграции, health/readiness, резервирование БД и файлов, проверенное восстановление, обновление/откат. Без Redis/Kubernetes как обязательных зависимостей. Локальный запуск и VPS имеют одинаковую модель данных.

Публичный репозиторий: README EN/RU, LICENSE (решение владельца), CONTRIBUTING, SECURITY, CODE_OF_CONDUCT, issue/PR templates, CI, synthetic demo, starter manifest, инструкции агентов, шаблоны docs/planning. Никаких production DB, клиентских материалов и личных путей.

## 13. Безопасность
Пароли через стойкий KDF; сессии HttpOnly/SameSite, Secure на HTTPS, защита от CSRF и ограничение попыток входа. Membership на сервере и PostgreSQL RLS как второй слой. Агентский token не даёт больше прав, чем его владелец.

Активный проектный HTML не выполняется на origin панели. Скриншоты защищены теми же правами, что метаданные; sandbox для активного превью, безопасный обмен сообщениями. Импорт не разархивирует пути за пределы каталога, не читает symlinks/секреты и не скачивает произвольные URL сервером. SVG не вставляется inline. Текст комментариев не становится инструкцией привилегированному серверу.

## 14. Миграция Concepts
Отдельный приватный импорт текущего live release: 839 screen IDs, 49 flows, E/J и темы, 491 asset в обследованном checkout (числа перепроверяются на живом релизе). Согласованный SQLite snapshot, comments+events, авторские подписи, версии, даты и legacy mapping. Assет-комментарии находятся в том же legacy хранилище с отдельным namespace.

Dry run и отчёт сверки; тестирование на копии; короткая остановка записи перед финальным снимком; атомарное переключение с сохранением старого сервиса/БД. Старые hash links переводятся клиентским compatibility route. Презентации, архивы и редактор персонажей остаются доступны. После новых записей откат требует согласования delta, а не возврата пустой/старой БД.

## 15. Приёмка
Рабочий путь clean clone → запуск → проект → screen/asset note → MCP claim → result → human acceptance. Веб-редактирование документа и плана видно агенту; конфликт не теряет данные. Другой пользователь не видит чужие проекты ни через UI, ни через API/MCP/files/history. Restore и archive не стирают историю. Прогресс совпадает с реальными story status и scope. Миграция сохраняет каждое обсуждение экрана/ассета и событие.

Запрещено объявлять проект завершённым только по наличию файлов/экранов. Нужны тесты, браузерные проверки ролей и восстановление резервной копии. Каждый этап имеет отдельный честный статус.

## 16. Уточнения после архитектурной сверки
- Визуальная цель уникальна по `(projectId, screenId, variant, palette)`. В API это отдельный screen object с key `screenId:variant:palette` и `data.screenId`; версии принадлежат этому представлению. Одинаковый базовый screenId не объединяет обсуждения тем.
- Историческая запись доступна только при пересечении текущих прав объекта и видимости самой ревизии. Ранее внутренние версии не открываются заказчику после публикации новой версии; diff не раскрывает скрытую сторону.
- Restore восстанавливает только содержимое, не статус приёмки, видимость, права, lease, evidence и системные поля. Переходы выполняются специализированными авторизованными операциями. Агентский токен всегда agent principal, даже если его создал администратор.
- Source/actor/evidence trust задаются сервером. Агент не может выдавать свою проверку за CI/human и не может принять правило через restore, import или generic patch.
- Story имеет один epic и не более одного текущего sprint; epic одну wave; feature links many-to-many без дублей. Архив epic/wave исключает потомков из effective active scope, сохраняя их собственный архивный флаг. Архив sprint не архивирует stories. Scope changes фиксируются для истории прогресса.
- Legacy author display name остаётся неподтверждённой импортированной подписью. Private principal/request ID/event IDs сохраняются в закрытом provenance, а не превращаются в новые учётные записи. Orphan target становится архивной заглушкой с отчётом. Файлы сверяются по SHA-256 и размеру.
