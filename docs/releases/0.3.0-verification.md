# 0.3.0 workspace experience verification

## Implemented

- Ordered screen/flow catalogs, discoverable alternate states, and clickable tags on cards and the viewer. Search cancellation prevents a pending query from replacing a selected tag. Editors are scoped to their project.
- English and Russian application UI; source project text remains unchanged. Account language, light/dark/system theme and accessible custom accent preferences are versioned and persisted.
- Personal display name, normalized raster avatar, session list/revocation, password changes, authenticator TOTP and one-use recovery codes. Human-only account APIs reject agent tokens. Account changes clear the previous identity's cached data and sensitive forms.
- Six original illustrations, responsive dashboard, a first-login introduction and an 11-chapter guide. Checklist requests use `limit=1` and reflect accessible project materials, never invented progress.
- Pinned-source VPS installer, protected bootstrap, domain checks, Caddy HTTPS and backup configuration/key preservation. See the installation limits below.
- Portable agent rules require semantic HTML, keyboard/focus checks, loading/error states, scoped caches, request cancellation and measured rendering/performance work.

## Verification

Passed: 90 server/API tests, 74 frontend unit tests, 40 CLI tests, 34 SDK tests, 9 MCP tests, 18 setup checks, 8 migration checks and 58 Playwright browser scenarios. Build, TypeScript checks and production dependency audit passed. Actual local API browser verification covered avatar upload/removal, persisted appearance, TOTP setup/confirmation and recovery-based disable without page or server errors.

The release uses behavioral tests, a production build, TypeScript checks, browser regressions in both languages at mobile/desktop sizes, and independent security/database/operations/hygiene review. Account cryptography, replay protection, lockouts, concurrency, RLS and avatar validation are covered by isolated PostgreSQL tests. Browser tests include account switching, stale form versions, recovery UI, project isolation, tag navigation, and catalog request counts.

An independent PostgreSQL 18 upgrade rehearsal preserved 10,000 synthetic sessions through schema 4 → 5, assigned unique public session IDs and accepted a repeated migration. The observed migration took 205 ms in that disposable local environment; this is not a production latency or zero-downtime guarantee.

## Installation limits

The installer passed input/retry/permission tests, including a real container running the bootstrap helper as an unprivileged user. PostgreSQL bootstrap retries and backup/restore were rehearsed. A complete clean systemd VPS run, Docker installation through apt, public DNS and public ACME issuance have **not** been verified in this environment. The installer reports success only after HTTPS readiness. Domain ownership/DNS changes remain the operator's responsibility.

## Upgrade and preservation

Schema 5 is additive but the previous application expects schema 4. Back up the database and matching `REPOSITORY_ENCRYPTION_KEY` before upgrading. Do not run an older migrator or restore an old database over newer writes; prefer a schema-compatible forward fix. Restore instructions require the original encryption key.

Existing catalogs may omit `data.order`; deterministic natural-key fallback remains supported. An ordering backfill must preserve IDs, files, notes and all other data, use `baseVersion`, and stop on concurrent changes. Original source ordering is project data, not bundled customer content.
